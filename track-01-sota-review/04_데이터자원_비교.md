# 네 저장소(MR-DTR / CausalMed / DrugRecommendation / HI-DR)의 데이터 자원 비교

> 대상: `Desktop\SOTA`의 MR-DTR(WWW'25), CausalMed(CIKM'24), DrugRecommendation=SubRec(NeurIPS'25) + `Desktop\HI-DR`의 HEIDR 공식 구현(AAAI'25, *"HI-DR: Exploiting Health Status-Aware Attention and an EHR Graph+ for Effective Medication Recommendation"*, Taeri Kim et al., 한양대)

## 0. 결론부터: 왜 겹치는가

네 저장소는 서로 다른 팀이 다른 학회(WWW'25, CIKM'24, NeurIPS'25, AAAI'25)에 낸 독립적인 논문의 코드지만,
전처리 파이프라인은 사실상 동일한 조상 코드베이스인 **[SafeDrug](https://github.com/ycq091044/SafeDrug)**(및 그 이전 **GAMENet**) 계열을 그대로 상속하고 있습니다.

- `MR-DTR/README.md`: *"The files required is the same as [SafeDrug]... the SMILES file needs to be processed as provided in SafeDrug using DrugBank."*
- `HI-DR/README.md`의 Dataset Preparation 섹션도 SafeDrug와 완전히 같은 파일 목록(`PRESCRIPTIONS.csv`, `ndc2atc_level4.csv`, `drug-atc.csv`, `drug-DDI.csv` 등)을 요구.
- 핵심 매핑 파일 3종은 **네 저장소 모두에서 파일 크기가 1바이트도 다르지 않습니다**:

  | 파일 | 크기 | CausalMed | MR-DTR | DrugRecommendation | HI-DR |
  |---|---|:---:|:---:|:---:|:---:|
  | `drug-atc.csv` | 19,612 B | ✅ | 참조만 | ✅ | ✅ |
  | `ndc2atc_level4.csv` | 12,513,289 B | ✅ | 참조만 | ✅ | ✅ |
  | `ndc2rxnorm_mapping.txt` | 109,954 B | ✅ | 참조만 | ✅ | ✅ |

  즉 네 논문 저자 모두 이 파일들을 직접 만든 게 아니라 SafeDrug/GAMENet 원본을 그대로 복사해 쓰고 있습니다.
- 더 결정적인 정황: MR-DTR의 그래프 전처리 스크립트가 참조하는(그러나 실물은 없는) SMILES 매핑 파일명이 `atc3toSMILES2.pkl`인데, **HI-DR의 `data/processing_iv.py:463`가 실제로 생성하는 파일명이 정확히 `mimic-iv/atc3toSMILES2.pkl`로 동일**합니다. 우연이라기엔 너무 구체적인 이름 일치라, MR-DTR 저자가 SafeDrug뿐 아니라 HEIDR류 후속 구현의 변수명까지 그대로 물려받았을 가능성을 시사합니다.

이 때문에 넷을 비교하면 "raw MIMIC 데이터를 벡터화하는 공통 전처리 단계"와 "각 논문의 고유 아이디어를 위해 추가로 만든 자원"이 뚜렷하게 갈립니다.

| `drug-DDI.csv` (DrugBank) | ✅ | ✅ | ✅ | ✅ | DDI 라벨 — 완전 공통, 넷 다 리포에 실물은 없고 경로만 참조 |

**추가로, HI-DR 저장소만의 특이점:** 다른 세 저장소와 달리 `Desktop\HI-DR` 최상위에 **실제 MIMIC-IV 원본 테이블이 통째로(수백 MB~3.5GB) 로컬에 존재**합니다 (`prescriptions.csv` 2.4GB, `poe.csv` 3.5GB, `pharmacy.csv` 3.3GB, `diagnoses_icd.csv` 149MB 등). 이는 다른 세 개가 "논문 재현용으로 클론만 해온 참조 코드"인 반면, HI-DR은 사용자가 **직접 크리덴셜받은 MIMIC-IV로 실제 구동 중인 활성 연구 프로젝트**이기 때문입니다. (→ 이 raw csv들은 PhysioNet DUA상 재배포 금지 대상이므로 어떤 경우에도 git에 커밋하거나 외부로 옮기면 안 됩니다.)

## 3. 전처리 산출물 (모델이 실제로 로드하는 최종 pkl)

| 산출물 | CausalMed | MR-DTR | DrugRecommendation | HI-DR | 역할 |
|---|:---:|:---:|:---:|:---:|---|
| `voc_final.pkl` | ✅ | 스크립트만 | ✅ | ✅ | 진단/시술/약물 어휘집(word↔idx) |
| `records_final.pkl` | ✅ | 스크립트만 | ✅ | ✅ | 환자별 방문 시퀀스 |
| `ddi_A_final.pkl` | ✅ | 스크립트만 | ✅ | ✅ | 약물쌍 DDI 인접행렬 |
| `ehr_adj_final.pkl` | ❌ | ✅ 필요(`preprocess_graph.py:14`) | ✅ | ✅ | 약물 동시처방 공출현(co-occurrence) 그래프 |
| `ddi_mask_H.pkl` | ✅ | 필요하지만 생성 스크립트 없음 | ✅ | ✅ | 약물 화학 하위구조(BRICS) 기반 마스크 |
| `data_final.pkl` | 생성 라인 주석 처리 | 필요하지만 실물 없음 | ✅ | ✅ | 위 결과를 합친 중간 DataFrame |

**해석 업데이트:**
- `voc_final.pkl`, `records_final.pkl`, `ddi_A_final.pkl` 세 개는 **네 논문 모두의 진짜 공통 핵심 자원**입니다.
- `ehr_adj_final.pkl`은 CausalMed만 안 씁니다 — 자기만의 인과 그래프로 대체했기 때문. **MR-DTR·DrugRecommendation·HI-DR은 셋 다 공출현 그래프를 씁니다** (단, HI-DR은 이걸 그대로 안 쓰고 아래 4번처럼 "가중치+방향성"을 추가한 자기만의 버전으로 한 단계 더 발전시킴).
- `ddi_mask_H.pkl`은 CausalMed·DrugRecommendation·HI-DR 세 저장소 모두 `ddi_mask_H.py`(로직 거의 동일, 파일 경로만 조금씩 다름)로 직접 생성하고, MR-DTR만 이 생성 스크립트가 없어 재현 시 구멍이 있습니다.

## 4. 각 저장소만의 고유 자원

### CausalMed 고유
- `causal_graph.pkl`, `Diag_Med_causal_effect.pkl`, `Proc_Med_causal_effect.pkl`
  → 진단→약물, 시술→약물 간 **인과 효과(causal effect) 그래프**를 미리 계산해 저장. 다른 세 저장소엔 없는 개념.

### MR-DTR 고유
- `ADMISSIONS.csv` 기반 타임스탬프 — `records_final.pkl`의 각 방문 레코드에 timestamp가 4번째 요소로 추가(`processing_mimic-iii.py:276`).
- `preprocess_graph.py`: 시간 정보를 반영한 "co-guided temporal graph"를 별도로 구성하는 2차 전처리.

### DrugRecommendation(SubRec) 고유
- `substructure_smiles.pkl`: BRICS 하위구조(fragment) SMILES 집합 자체를 1급 객체로 저장해 모델(`MedRecCGIBModel.py`)이 직접 로드.
- `atc2rxnorm.pkl`: 역방향 매핑(다른 저장소는 ndc→atc 방향만 가짐).

### HI-DR(HEIDR) 고유
- **`weighted_confidence_directed_ehr_graph.pkl`** (MIMIC-III), **`mimic_iv_weighted_confidence_directed_ehr_graph.pkl`**(MIMIC-IV)
  → 논문 제목의 "**EHR Graph+**"에 해당하는 핵심 산출물. 단순 공출현 인접행렬(`ehr_adj_final.pkl`)에서 한 단계 더 나아가, 엣지에 **방향성(directed)**과 **신뢰도 가중치(confidence weight)**를 부여한 그래프. `HEIDR_main.py:188-192`에서 `np.argwhere(...!=0)`로 엣지 인덱스를, 같은 행렬 값으로 엣지 가중치를 직접 만들어 GNN 입력으로 사용. 다만 저장소 어디에도 이 파일을 **생성하는** 스크립트는 보이지 않아(로드하는 코드만 3곳에서 발견) 사전 계산되어 배포된 산출물로 추정됩니다.
- `records_final2_hadm_ids.pkl` (MIMIC-IV 전용): 방문 레코드에 원본 `hadm_id`(입원 식별자)를 별도로 보존 — 다른 세 저장소는 전처리 후 원본 식별자를 버리는 반면, HI-DR은 이후 단계(아래)에서 원본 EHR 테이블과 재조인하기 위해 유지.
- **`HEIDR/drug_filter/`, `HEIDR/service_personalization/`, `Pretrain_embedding_codes/`**: 이건 HEIDR 논문 자체의 공식 구현 범위를 넘어서는, **이 저장소 사용자가 직접 얹은 후속 확장 모듈**로 보입니다(`candidate_pool.py`, `drug_filter.pt`, `order_head_model.py`, `service_matching.py` 등 — DDI 인지 후처리 필터, 이력 기반 후보풀 확장, 처방 서비스 개인화 등). 데이터 자원 관점에서 보면 `candidates_*.pt`, `drug_filter.pt`, `order_head*.pt`, `visit_embeddings.pt` 같은 **PyTorch 텐서 체크포인트**들이 새로 추가되는데, 이는 다른 세 저장소의 "논문 재현용 pkl 자원"과는 성격이 달라(학습된 모델 가중치/중간 임베딩) 이 비교표의 범위에서는 제외했습니다.

## 5. 이름은 다르지만 "같은 역할"을 하는 파일들

`med_structure_file`(약물 코드 → SMILES 분자 구조 매핑) 역할을 하는 파일이 저장소마다 이름이 다릅니다:

| 저장소 | 파일명 | 실물 존재 |
|---|---|:---:|
| CausalMed | `idx2drug.pkl` | ✅ |
| DrugRecommendation | `idx2SMILES.pkl` | ✅ |
| HI-DR (MIMIC-III) | `idx2drug.pkl` | ✅ |
| HI-DR (MIMIC-IV) | `atc32SMILES.pkl` → 산출물 `atc3toSMILES2.pkl` | ✅ |
| MR-DTR | `atc3toSMILES2.pkl` | ❌ (참조만, **HI-DR의 MIMIC-IV 산출물명과 완전히 동일**) |

CausalMed와 HI-DR은 MIMIC-III 파트에서 파일명(`idx2drug.pkl`)까지 똑같이 씁니다. MR-DTR이 참조하는 이름은 CausalMed식(`idx2drug`)이 아니라 **HI-DR의 MIMIC-IV 산출물명(`atc3toSMILES2.pkl`)과 정확히 일치**한다는 점이 흥미로운 단서입니다.

**한 줄 결론:** 네 저장소는 "진단·시술·처방 시퀀스 + DDI 라벨"이라는 SafeDrug 계열 공통 데이터 기반 위에서, 각자 **CausalMed=인과그래프, MR-DTR=타임스탬프+시간그래프, SubRec=약물 하위구조 저장, HI-DR=방향성·가중치 EHR 그래프(+ 논문 밖 후속 확장 모듈)**라는 자기만의 자원 한 겹을 추가로 쌓아 논문의 핵심 기여를 구현한 구조입니다. 특히 MR-DTR과 HI-DR 사이의 파일명 일치(`atc3toSMILES2.pkl`)는 두 저장소가 SafeDrug보다 더 가까운 계보를 공유했을 가능성을 보여주는 흥미로운 단서입니다.
