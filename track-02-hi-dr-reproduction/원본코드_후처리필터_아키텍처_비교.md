# 원본 HI-DR 코드 vs 후처리 필터 레이어 — 아키텍처 비교

## 1. 목적

이 문서는 "원본 HI-DR(HEIDR) 모델 코드"와 "이번 작업(사후 필터, `HEIDR/drug_filter/`)"이 정확히 어떤 관계인지 정리한다. 결론부터 말하면: **원본 코드는 한 글자도 수정하지 않았고, 그 출력 위에 완전히 독립된 후처리 레이어를 새로 얹었다.**

---

## 2. 원본 HI-DR(HEIDR) — 무엇을 하는 코드인가

| 파일 | 역할 |
|---|---|
| `HEIDR/HEIDR_model.py` | 핵심 모델 클래스 `HEIDR(nn.Module)`. `encode()`(방문 시퀀스 → 질병/시술 임베딩, cross-visit attention, drug memory), `decode()`(약물 시퀀스 생성용 트랜스포머 디코더) 정의 |
| `HEIDR/beam.py` | `Beam` 클래스 — 방문별로 빔서치를 진행하며 후보 약물 시퀀스와 각 위치의 확률을 관리 |
| `HEIDR/util.py` | 데이터 전처리, 평가지표(`sequence_metric`, `ddi_rate_score` 등) |
| `HEIDR/HEIDR_main.py` | 원본 학습 스크립트 |
| `HEIDR/recommend_heidr.py` | 원본 추천/평가 스크립트(`test_recommend_batch` 등, 논문 벤치마크 재현에 쓰인 검증된 레퍼런스 구현) |

**입력 → 출력**: 환자의 진단/시술 히스토리(및 VITA가 뽑아둔 top-k 유사 방문) → `encode()`로 방문 임베딩 생성 → `Beam`으로 `decode()`를 반복 호출하며 방문별 약물 시퀀스(각 약물의 확률 포함)를 생성. 이게 순수 HI-DR의 전부다 — DDI는 이 단계에서 전혀 고려되지 않는다.

**학습된 가중치**: `HEIDR/saved/heidr_top_3_att_20_gumbel_06/Epoch_43_..._JA_0.6238_..._.model` (기존에 학습·검증 완료된 체크포인트, 이번 작업에서 재학습하지 않음).

---

## 3. 후처리 필터 레이어 — `HEIDR/drug_filter/`

| 파일 | 역할 |
|---|---|
| `generate_candidates.py` | **유일하게 원본 클래스(`HEIDR`, `Beam`)를 직접 호출하는 지점.** beam search 결과(방문별 약물 후보+확률, 방문 임베딩)를 `candidates_{train,eval,test}.pt`로 캐싱 |
| `filter_model.py` | `DrugFilterHead` — 후보 하나가 "실제 정답 처방일 확률"을 내는 작은 이진분류기(2-layer MLP) |
| `ddi_features.py` | 같은 방문 내 다른 후보와의 DDI 충돌 강도를 피처 2개로 계산 |
| `dataset.py` | `DrugFilterHead` 학습용 (방문×후보) 샘플 데이터셋 |
| `train_filter.py` | `DrugFilterHead` 학습 (10 epoch, 117k 샘플, ~17초) |
| `select_threshold.py` | 필터 threshold 선택 로직들(F1-only, DDI-aware constrained argmax) + 평가용 순수 함수 |
| `evaluate_filter.py` | 필터 전/후 지표(precision/recall/jaccard/f1/ddi_rate/avg_med) 비교 |
| `significance_test.py`, `split_robustness.py`, `absolute_ddi_exposure.py` | 통계적 유의성·재현성·절대 DDI 노출량 검증 스크립트 |

**입력 → 출력**: `candidates_*.pt`(HI-DR이 이미 생성해둔 후보+확률) → `DrugFilterHead`가 각 후보를 재채점 → threshold로 최종 처방 목록 확정. **HI-DR을 다시 실행하지 않는다** — 캐싱된 파일만 읽는다.

---

## 4. 두 레이어의 접점 — `generate_candidates.py`

원본 코드와 후처리 레이어가 만나는 곳은 **딱 한 파일**이다:

```python
# HEIDR/drug_filter/generate_candidates.py
from HEIDR_model import HEIDR      # 원본 클래스, 그대로 import
from beam import Beam              # 원본 클래스, 그대로 import
...
model = HEIDR(voc_size, ehr_adj, ddi_adj, ddi_mask_H, topk=TOPK, ...)
model.load_state_dict(torch.load(CHECKPOINT))   # 기존 학습된 가중치 그대로 로드
...
input_disease_embdding, ..., drug_memory, ... = model.encode(...)   # 원본 메서드 그대로 호출
...
beams = [Beam(BEAM_SIZE, ...) for _ in range(visit_num)]            # 원본 클래스 그대로 사용
```

**여기서 원본과 다른 유일한 지점**: `model.encode()`/`model.decode()` 호출을 `torch.no_grad()`로 감싸지 않는다. 이 체크포인트에서 `no_grad`를 쓰면 빔 위치 0번을 제외한 전부가 NaN을 내는 버그를 Task 5에서 발견했기 때문이다(`.backward()`는 어차피 안 부르므로 안전, 메모리 누적 방지를 위해 저장하는 텐서만 `.detach()`). **원본 파일(`HEIDR_model.py`, `beam.py`) 자체는 고치지 않고, 이 새 스크립트에서 호출하는 방식만 다르게 한 것**이다.

## 6. 전체 파이프라인

```
[1회만 실행, beam search — 원본 코드]
환자 히스토리 + VITA top-k 유사방문
        │
        ▼  HEIDR.encode() / HEIDR.decode() (원본, 가중치 그대로)
        │  Beam 클래스로 방문별 후보 약물 시퀀스 + 확률 생성 (원본, 그대로)
        ▼
candidates_{train,eval,test}.pt  ← 캐싱, 이후 전부 이 파일만 재사용
        │
        │  ※ 여기서부터는 HI-DR을 다시 호출하지 않음
        ▼
[후처리 필터 레이어 — 새로 작성]
DrugFilterHead 학습 (HI-DR 확률 + DDI 충돌 피처 → 정답 확률 재채점)
        │
        ▼
threshold 선택 (F1-only / DDI-aware constrained argmax / greedy 등)
        │
        ▼
최종 처방 목록
```

## 7. 비교 요약

| | 원본 HI-DR | 후처리 필터 레이어 |
|---|---|---|
| 위치 | `HEIDR/*.py` (최상위) | `HEIDR/drug_filter/` (하위 모듈) |
| 이번 작업에서 수정 여부 | **없음** (git log로 확인) | 전부 새로 작성 |
| 학습 대상 | 원본 체크포인트(기존 학습 완료, 재학습 안 함) | `DrugFilterHead`만 별도 학습(17초/1회) |
| DDI 고려 여부 | 전혀 없음 | 입력 피처 + threshold 선택 제약으로 반영 |
| beam search 재실행 | 최초 후보 생성 시 1회만 | 없음 (캐싱된 후보만 재사용) |
| 실패 시 원복 범위 | - | 이 레이어를 통째로 빼도 원본 HI-DR 동작에 영향 없음 |

**설계상 의미**: 이런 구조 덕분에 (1) HI-DR 자체의 검증된 성능(원 논문 벤치마크)이 훼손될 위험이 없고, (2) 가장 비용이 큰 연산(beam search, train split만 1시간+)을 반복하지 않고도 필터 쪽 실험(임계값 튜닝, DDI-aware 설계, 오늘 밤의 절대 노출량/greedy 비교 등)을 몇 초~몇 분 단위로 반복할 수 있었다.
